# Onsite Robots.txt Audit

Audit checks 10.1–10.7 for a supplied site. Use Python for raw robots collection/candidate preparation, Screaming Frog for crawl permissions and directives, and agent reasoning for classification and policy decisions. Use bounded read-only HTTP checks for missing static page identity, response or redirect evidence before requesting a new SF run; follow the static follow-up boundary in delivery-boundaries.md. Do not replace SF with a custom noindex/canonical crawler.

## Fixed checklist item names

Preserve these exact user-provided names in the report and checklist tables. Prefix with the check ID; do not paraphrase, shorten, correct grammar or translate the item name. Report language applies to Findings/Coverage, not these titles. Existing Yes/No/NA/Human Check decision rules still apply; in 10.2, Yes means no unintended blocking.

| ID | Check |
| --- | --- |
| 10.1 | Does a robots.txt document exist? |
| 10.2 | Are sections of the site that we want indexed, being disallowed with robots.txt? |
| 10.3 | Are disallow blocks in place for URLs that Google shouldn't be crawling? |
| 10.4 | Are we allowing bot access to CSS and JS documents? |
| 10.5 | Are the following pages disallow? shopping carts, thank you, admin, duplicate content, account pages. |
| 10.6 | Is the robots.txt called robots.txt, and not ROBOTS.TXT? |
| 10.7 | Is there a link in the robots.txt file to the sitemap index/sitemap? |

## Inputs and shared configuration

Use [config.template.json](config.template.json), or the user's integrated config with robots settings. The standalone template omits HTTPS-only keys and unimplemented collector switches. This skill executes only robots checks, even when the shared config includes enabled HTTPS keys. Set checks.robots_txt=true. Preserve the shared MCP endpoint, allowed-base directory, existing crawl and AUDIT_PYTHON runtime; never copy a different machine's absolute paths.

Read [robots rules](references/robots-rules.md) for classifications, candidate paths and Yes/No/NA/Human Check boundaries. Read [delivery boundaries](references/delivery-boundaries.md) for minimum per-check evidence, scoped NA, optional bot policy and delivery before manual follow-up. Read [report schema](references/report-schema.md) before writing findings.json. For live SF retrieval, read [MCP guide](references/screaming-frog-mcp.md); supplied exports do not require an MCP connection. For a new runtime, read [Python runtime](references/runtime-python.md).

Before requesting new SF evidence, read [the shared SF prerequisite](references/sf-first-run-setup.md). Reuse suitable existing crawl/exports without loading a profile or verifying every historical setting. If an evidence gap still requires SF-specific fields or rendering after existing exports and permitted static follow-up, delegate preparation to the independent `sf-shared-config` skill: default main for full-site preparation, targeted profile only for a necessary follow-up, then user confirmation of sitemap, manual Start and saved-file handover. Never automatically start a general/List crawl or use sf_crawl(config_path) as a loader. Any config-load failure immediately gets manual Load + sitemap guidance, with no native retry/pending loop. Preserve active crawls and shared site-specific sitemap settings. Configuration failure does not erase available evidence; verify only settings material to each decision.

## Workflow

If a shared-preparation/manual-evidence step would pause for the user, finish the available checks and deliver the current final Excel with Human Check first. Include the pending preparation or URL-list instructions in handover; update after the user replies. This rule applies before invoking a prerequisite that itself waits for user input.

1. Create a unique writable run directory; save resolved config, audit date in the user's timezone and provenance. In an integrated run, reuse the orchestrator's manifest, raw evidence, cache and cumulative usage.json. Do not reset request/MCP budgets for each skill or load shared SF crawls concurrently.
2. Run [collect_robots.py](scripts/collect_robots.py) to archive /robots.txt once per scoped origin, extract Sitemap declarations and write bounded candidate URL lists. This helper does not test candidates, crawl sitemaps, or judge effective Googlebot permissions. Record its errors and remaining coverage. Collector caching is fixed per-run; it does not implement TTL, force-refresh, automatic retries or a consecutive-error counter. Obtain fresh evidence in a new run without resetting an integrated budget. A recognised directive is not necessarily a complete valid robots group; interpret effective rules from sufficient evidence and verify SF behavior only when that interpretation depends on its crawl results.
3. Reuse completed SF crawl/sitemap exports to identify important pages and special-page candidates, including category landing pages, /page/ and page/paged parameters. Apply the pagination/category loop boundaries in the robots reference: visited-set deduplication, bounded series/variant samples, no unlimited page-number/filter generation. Do not blanket-block useful category/pagination pages. Without a usable sitemap, build a temporary local inventory from existing public-link evidence; further SF discovery requires shared preparation and a user-run bounded crawl, never a published sitemap. For missing candidate evidence, inspect existing exports first, then use permitted finite read-only static checks for identity/responses/redirects; request a user-run SF List follow-up only for remaining SF-specific or rendering needs. source.allow_new_crawl controls whether to request new discovery/List evidence, not permission for autonomous Start; otherwise reuse exports and permitted static checks, then save any remaining list and unresolved gaps.
4. Collect candidate responses and the robots/directive/canonical/resource fields material to each decision, following the minimum evidence table. Do not require every field for every URL or verify alternative controls after one sufficient policy is established. Reuse this metadata first. For a remaining static identity/response/redirect gap, use the bounded read-only route before shared SF preparation; request SF/rendered content only if that route cannot supply the material evidence. Only unresolved classifications/content comparisons require targeted HTML batches; content_batch_size is not a total evidence limit. Use shared preparation for any user-run supplemental crawl, preserve original crawl/profile provenance and coordinate any return to the main profile without overwriting the user's sitemap. The targeted shared profile stores source/rendered HTML; existing static evidence does not require it. Use the actual tool schema and export fields. Noindex-filter-only data is insufficient to judge the remaining candidates. Determine effective Googlebot permissions from sufficient rule evidence; verify SF user-agent/robots mode only when relying on those SF results for that decision. Rendering configuration is needed for claims about dynamically rendered content, not every static result. Unknown configuration alone is not a missing-evidence condition: identify the specific conclusion it prevents before requesting it. Missing fields, unexplained nulls and URLs missing from the crawl are unknown, not a pass or 404; a verified complete extraction's documented empty-directive value can establish absence for that field and scope. A shared handover is not proof of complete audit evidence.
5. Apply checks 10.1–10.7, using response/content evidence to exclude soft 404s and classify real pages. Enumerated path names and default/plugin robots rules alone cannot establish existence or purpose: add-to-cart or woocommerce paths do not prove an active cart. Follow the template-rule boundary in the robots reference. Empty, whitespace-only and comment-only robots.txt produce No plus an Empty robots.txt issue under this audit standard. For 10.2, sitemap URLs allowed by effective Googlebot rules pass without extra purpose/content gates; NA is limited to confirmed absent robots or explicit waiver. For 10.3, the agent first selects applicable sample families based on actual site nature/functions and records the rationale/exclusions; cart/checkout/account are not required for every site, and collector seeds are only a candidate superset. For sites without supported shopping functionality, do not require/add cart rules or count existing shopping rules as applicable pass evidence; when site evidence confirms unused/inapplicable template remnants, set 10.3 No/X, explicitly name the residual directives and why they are inapplicable in concise Findings, and add the actual directives, applicability evidence and targeted cleanup action to 10. Robot.txt. Put discovery sources/counts in Coverage. Suspected remnants with unverified purpose remain Human Check only in Checklist. Selected finite enumeration examples all effectively blocked pass for that sample only when no confirmed 10.3 defect remains; confirmed unused template rules override that sample pass; a readable file with no non-empty effective Googlebot Disallow is No under the agreed audit standard, with an issue and further-validation recommendation, never an inferred security exposure. Disallow controls crawling, not private access or proven deindexing.
6. Finish the current bounded evidence pass and deliver before waiting for a user-run supplemental crawl, business-policy reply or missing export. Write agent-reviewed findings.json, then run [build_report.py](scripts/build_report.py). Use its explicit --site-url delivery completion with the actual audited URL and --prepared-input to archive the completed input: missing requested rows become Human Check with reason/action details in Checklist, without dropping confirmed defects. Review/translate generated wording as required. Every NA requires a specific reason; No requires confirmed linked issue evidence. Errors/unknowns go to evidence_gaps.json and the final workbook as Human Check with concise conclusion, missing/failed evidence and next action in Checklist Findings only, never the defect sheet. Preserve completed counts, sources and checked/unresolved scope in Coverage; keep supported conclusions in Findings without repeating Coverage. For 10.4, read the CSS/JS identity/source-scope boundary in robots-rules.md: distinguish HTML login/reset pages from assets, exclude only verified private-page-only assets, keep shared public-page assets in scope, and never treat an effectively blocked resource as allowed because an HTTP fetch succeeded. Specify SF errors or missing resource/type/source/permission evidence as concrete Checklist gaps. Do not withhold final export for unresolved evidence. Scope limitations cannot be converted into Yes. The report generator validates schema and associations, not the correctness of agent reasoning.
7. Verify workbook headers/values and readable layout, save raw evidence and handover, and return the report plus material limitations. Do not claim real Google index status from SF directives. No login, form submission, registration or order creation. Do not modify website/server settings.

## Delivery

Exactly two sheets, no extra columns:

| Sheet | Headers |
| --- | --- |
| Checklist | Check; Result; Findings; Coverage |
| 10. Robot.txt | Issue; Issue Description; How to Fix; Address |

Results are Yes/No/NA/Human Check; never leave Result blank. Always export every requested check, even if all need human review. Every Human Check requires a visible human_check_reason and concrete next action in Checklist Findings, and the specific evidence gap. Findings should normally use one to three short lines: conclusion, cause/gap and necessary next action. Coverage owns already-checked sources, counts, sampling, verified/unresolved scope and exclusions; do not repeat that inventory in Findings. Review details never create a row in 10. Robot.txt. No remains a confirmed defect and requires an associated defect row on that sheet. If No also has gaps, retain the defect and record Human Check only in Checklist Findings. NA requires a reason and creates no defect row. The builder can migrate legacy kind=human_check issue objects into Checklist, preserving details without exporting them as defects. Do not omit unresolved checks or call delivery an overall pass. Group confirmed defects only by same cause/action; preserve known affected URL/query strings and qualify candidates. Keep both sheet headers even when no defects exist. Protect against formula-like input.

Findings wording must be understandable to a reader without SEO or crawler knowledge: state what was found first, why it matters to this check, and a concrete next step only when needed. Prefer "Google cannot crawl this page" to "effective Googlebot permission denied", and "we do not yet know which public pages use these files" to "missing resource inlinks". Preserve distinctions between crawling, indexing and login protection; do not translate allowed crawling into indexed or ranking claims. Name specific paths/rules only when needed to identify the finding; explain technical terms in ordinary words. Avoid internal terms such as agent-reviewed, evidence gate, scope permission, applicable family and generic "further validate". Match the report language, keep one to three short sentences and do not repeat Coverage. See the plain-language examples in [report schema](references/report-schema.md#plain-language-findings).

Findings readability: use short labelled lines (Conclusion / Missing or failed / Next action; match the report language), without an Already checked recap or URL inventory. In each Checklist row, optional findings_bold lists exact existing phrases to emphasize: the key conclusion, blocked cause, or exclusion reason. Keep emphasis selective rather than bolding whole paragraphs or URL lists. The builder uses real Excel rich-text bold, automatically emphasizes known labels and falls back to a short leading conclusion for unstructured findings. Keep findings as plain text without Markdown bold markers; no extra columns or changed audit results.

Filename: `{site name}_robots_audit_{YYYY-MM-DD}.xlsx`. Use the user's site name or hostname without www. Never overwrite a previous report; use a new run directory. Match the requested report language. Keep machine setup messages out of customer-facing Findings/Coverage.
