# Onsite Robots.txt Audit

Audit checks 10.1–10.7 for a supplied site. Use Python for raw robots collection/candidate preparation, Screaming Frog for crawl permissions and directives, and agent reasoning for classification and policy decisions. Do not replace SF with a custom noindex/canonical crawler.

## Inputs and shared configuration

Use [config.template.json](config.template.json), or the user's integrated config with robots settings. Read [configuration ownership](references/config.md): share connection/runtime/site/source/budget/output settings, but keep per-flow check settings and dependency declarations. The standalone template omits HTTPS-only keys and unimplemented collector switches. This skill executes only robots checks, even when the shared config includes enabled HTTPS keys. Set checks.robots_txt=true. Preserve the shared MCP endpoint, allowed-base directory, existing crawl and AUDIT_PYTHON runtime; never copy a different machine's absolute paths.

Read [robots rules](references/robots-rules.md) for classifications, candidate paths and Yes/No/NA/Human Check boundaries. Read [delivery boundaries](references/delivery-boundaries.md) for minimum per-check evidence, scoped NA, optional bot policy and delivery before manual follow-up. Read [report schema](references/report-schema.md) before writing findings.json. For live SF retrieval, read [MCP guide](references/screaming-frog-mcp.md); supplied exports do not require an MCP connection. For a new runtime, read [Python runtime](references/runtime-python.md).

Before requesting new SF evidence, read [the shared SF prerequisite](references/sf-first-run-setup.md). Reuse suitable existing crawl/exports without loading a profile or verifying every historical setting. Otherwise delegate preparation to the independent `sf-shared-config` skill: default main for full-site preparation, targeted profile only for a necessary follow-up, then user confirmation of sitemap, manual Start and saved-file handover. Never automatically start a general/List crawl or use sf_crawl(config_path) as a loader. Any config-load failure immediately gets manual Load + sitemap guidance, with no native retry/pending loop. Preserve active crawls and shared site-specific sitemap settings. Configuration failure does not erase available evidence; verify only settings material to each decision.

## Workflow

If a shared-preparation/manual-evidence step would pause for the user, finish the available checks and deliver the current final Excel with Human Check first. Include the pending preparation or URL-list instructions in handover; update after the user replies. This rule applies before invoking a prerequisite that itself waits for user input.

1. Create a unique writable run directory; save resolved config, audit date in the user's timezone and provenance. In an integrated run, reuse the orchestrator's manifest, raw evidence, cache and cumulative usage.json. Do not reset request/MCP budgets for each skill or load shared SF crawls concurrently.
2. Run [collect_robots.py](scripts/collect_robots.py) to archive /robots.txt once per scoped origin, extract Sitemap declarations and write bounded candidate URL lists. This helper does not test candidates, crawl sitemaps, or judge effective Googlebot permissions. Record its errors and remaining coverage. Collector caching is fixed per-run; it does not implement TTL, force-refresh, automatic retries or a consecutive-error counter. Obtain fresh evidence in a new run without resetting an integrated budget. A recognised directive is not necessarily a complete valid robots group; interpret effective rules from sufficient evidence and verify SF behavior only when that interpretation depends on its crawl results.
3. Reuse completed SF crawl/sitemap exports to identify important pages and special-page candidates, including category landing pages, /page/ and page/paged parameters. Apply the pagination/category loop boundaries in the robots reference: visited-set deduplication, bounded series/variant samples, no unlimited page-number/filter generation. Do not blanket-block useful category/pagination pages. Without a usable sitemap, build a temporary local inventory from existing public-link evidence; further SF discovery requires shared preparation and a user-run bounded crawl, never a published sitemap. Missing candidates require user exports or a permitted user-run List follow-up. source.allow_new_crawl controls whether to request new discovery/List evidence, not permission for autonomous Start; otherwise save the list and leave dependent checks unresolved.
4. Collect candidate responses and the robots/directive/canonical/resource fields material to each decision, following the minimum evidence table. Do not require every field for every URL or verify alternative controls after one sufficient policy is established. Reuse this metadata first. Only unresolved classifications/content comparisons require targeted HTML batches; content_batch_size is not a total evidence limit. Use shared preparation for any user-run supplemental crawl, preserve original crawl/profile provenance and coordinate any return to the main profile without overwriting the user's sitemap. The targeted shared profile stores source/rendered HTML; existing static evidence does not require it. Use the actual tool schema and export fields. Noindex-filter-only data is insufficient to judge the remaining candidates. Determine effective Googlebot permissions from sufficient rule evidence; verify SF user-agent/robots mode only when relying on those SF results for that decision. Rendering configuration is needed for claims about dynamically rendered content, not every static result. Unknown configuration alone is not a missing-evidence condition: identify the specific conclusion it prevents before requesting it. Missing fields, unexplained nulls and URLs missing from the crawl are unknown, not a pass or 404; a verified complete extraction's documented empty-directive value can establish absence for that field and scope. A shared handover is not proof of complete audit evidence.
5. Apply checks 10.1–10.7, using response/content evidence to exclude soft 404s and classify real pages. Enumerated path names and default/plugin robots rules alone cannot establish existence or purpose: add-to-cart or woocommerce paths do not prove an active cart. Follow the template-rule boundary in the robots reference. Empty, whitespace-only and comment-only robots.txt produce No plus an Empty robots.txt issue under this audit standard. For 10.2, sitemap URLs allowed by effective Googlebot rules pass without extra purpose/content gates; NA is limited to confirmed absent robots or explicit waiver. For 10.3, selected finite enumeration examples all effectively blocked pass for that sample; a readable file with no non-empty effective Googlebot Disallow is No under the agreed audit standard, with an issue and further-validation recommendation, never an inferred security exposure. Disallow controls crawling, not private access or proven deindexing.
6. Finish the current bounded evidence pass and deliver before waiting for a user-run supplemental crawl, business-policy reply or missing export. Write agent-reviewed findings.json, then run [build_report.py](scripts/build_report.py). Use its explicit --site-url delivery completion with the actual audited URL and --prepared-input to archive the completed input: missing requested rows and review issues become Human Check, without dropping confirmed defects. Review/translate generated wording as required. Every NA requires a specific reason; No requires confirmed linked issue evidence. Errors/unknowns go to evidence_gaps.json and the final workbook as Human Check with Already checked, Missing/failed and Next action details and a linked human_check Issues row. Preserve completed counts and supported results. For 10.4, specify SF crawl/export errors or missing resource rows/relationships instead of generic resource-purpose uncertainty. Do not withhold final export for unresolved evidence. Scope limitations cannot be converted into Yes. The report generator validates schema and associations, not the correctness of agent reasoning.
7. Verify workbook headers/values and readable layout, save raw evidence and handover, and return the report plus material limitations. Do not claim real Google index status from SF directives. No login, form submission, registration or order creation. Do not modify website/server settings.

## Delivery

Exactly two sheets, no extra columns:

| Sheet | Headers |
| --- | --- |
| Checklist | Check; Result; Findings; Coverage |
| Issues | Issue; Issue Description; How to Fix; Address |

Results are Yes/No/NA/Human Check; never leave a delivered Result blank. Missing evidence is Human Check, not Yes/No/NA. Always export the final Excel with every requested check, even if any or all checks need human review. Every Human Check requires human_check_reason in Findings and an Issues row marked `Human Check`, explicitly explaining already-checked sources/counts/results, the exact missing or failed URL/response/content/control and a concrete manual verification action. If nothing was checked, say so. No remains a confirmed defect; if it also has evidence gaps, retain No and append Human Check in Findings plus a separate human_check issue. Issues kind=defect links only to No; kind=human_check links to Human Check or No. Never claim a review row is a proven website/security defect. Every No still requires a confirmed-defect Issues row; every NA still requires a visible reason. Coverage states counts, URL sources, full/sample scope, rendering and exclusions. Do not omit unresolved checks or call final export an overall audit pass. Group only same-cause/same-action entries; Address contains known actual/candidate URLs, one per line, with candidate existence clearly qualified. When individual URLs are unknown, use the actual audited origin or robots.txt address and explain the missing inventory, never guess URLs as verified pages. Keep both sheet headers when no issues exist. Protect against formula-like untrusted input and preserve URL/query strings.

Filename: `{site name}_robots_audit_{YYYY-MM-DD}.xlsx`. Use the user's site name or hostname without www. Never overwrite a previous report; use a new run directory. Match the requested report language. Keep machine setup messages out of customer-facing Findings/Coverage.
