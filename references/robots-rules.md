# Robots.txt checks 10.1–10.7

## Evidence workflow

Read this reference and [delivery boundaries](delivery-boundaries.md) when a robots audit is requested. Python fetches /robots.txt once per origin per run (including required CDN/subdomain origins), caches the raw response, URL, redirects, status and timestamp. Distinguish HTML error responses, empty content, comments, recognised directives and failures. A declared origin is scheme + host + port. Do not use simple substring matching or Python's basic robot parser as proof of Google's effective permissions. Prefer Screaming Frog robots results and matched directive evidence for Googlebot, recording relevant configuration when relying on SF behavior. A simple unambiguous live policy can instead be interpreted directly; unknown SF configuration must not block that independent decision. Complex or ambiguous matching still requires reliable rule evidence.

Read robots Sitemap declarations first, then reuse available sitemap/crawl URL exports. If no usable sitemap exists, prepare a local temporary inventory using public same-site links and existing SF crawl data. This is not a sitemap published to the website. Use configured discovery/request budgets, record page/depth limits and link exclusions, and avoid unbounded filter/query combinations. If no existing data can support discovery, a bounded public crawl needs source.allow_new_crawl; without it save candidates and leave affected checks unresolved. Never enable a new crawl silently.

Collect known candidate URLs from the crawl, sitemaps and a bounded path enumeration. Cache requests; do not treat missing URLs in an existing crawl as 404. Reuse candidate exports first, then use finite read-only static identity/response/redirect checks under [the retrieval boundary](delivery-boundaries.md#evidence-retrieval-order-and-bounded-static-follow-up) where sufficient. Only remaining SF-specific/rendering gaps need a user-run follow-up; any new SF List/discovery crawl uses [shared preparation](sf-first-run-setup.md), source.allow_new_crawl scope permission and manual user Start. Capture all candidate results, not only the Noindex filter. Discover actual tool/filter/field names using references/screaming-frog-mcp.md; do not invent a List Mode API. Provide the URL-list file for the user and accept its export; archive affected checks in evidence_gaps.json and deliver the final Excel with Human Check before waiting for follow-up evidence. No automated Start or indefinite waiting for manual completion.

Collect the fields material to each decision, as defined in delivery-boundaries.md: status/redirect/final address, effective robots permission, applicable meta/header directives, canonical or classification content as needed. This is not a mandatory all-fields-per-URL gate. Once one accepted control is established, do not require irrelevant alternative controls. Record missing material fields explicitly. Directives > Noindex supplies meta/header noindex findings. Response Codes > Blocked by robots.txt supplies blocking evidence. Use resource exports for CSS/JS and rendering mode for dynamic coverage. Indexability=Non-Indexable alone does not prove noindex (it can reflect redirects/canonical/blocking). A missing field or filter row is not proof that noindex is absent.

Separate an obey-robots crawl from any explicitly configured ignore-robots diagnostic crawl. A noindex found only while ignoring robots cannot establish that Google can read it. JS-inserted directives require rendering evidence; static-only exports leave that scope unverified. Do not claim deindexing has occurred without search-index evidence.

Missing sitemap, subtype, result or permission evidence is not NA. Human Check states completed work and the precise unresolved URLs/rules |
| 10.3 Are disallow blocks in place for URLs that Google shouldn't be crawling? | All selected finite enumeration examples are effectively blocked for Googlebot; label this rule-sample pass without requiring proof that synthetic pages exist | Confirmed unused/inapplicable template directives: No plus a defect row in 10. Robot.txt. No non-empty effective Googlebot Disallow or a verified should-not-crawl target allowed also gives No, with reason and appropriate action | Known absent file or explicitly waived check: NA with reason. Partly unblocked synthetic candidates with unverified existence/policy, or ambiguous matching: Human Check; show completed matches and missing validation |
| 10.4 Are we allowing bot access to CSS and JS documents? | Eligible intended-public-page CSS/JS confirmed allowed and usable; list excluded private-only resources | Required public-page CSS/JS confirmed effectively blocked or unusable; HTTP 200 alone cannot override robots blocking | Verified complete inventory with no linked necessary CSS/JS: NA with reason. Human Check normally means SF crawl/export error or required resource rows/relationships/permission results unavailable; specify completed checks, error and affected resources, not generic resource-purpose uncertainty |
| 10.5 Are the following pages disallow? shopping carts, thank you, admin, duplicate content, account pages. | Applicable classes meet the policies below | Confirmed class violates its policy | Completed bounded discovery without live-flow clues, or owner-confirmed inapplicability: NA with scope/limitations. Known transaction-only flow or missing candidate results/purpose: Human Check |
| 10.6 Is the robots.txt called robots.txt, and not ROBOTS.TXT? | /robots.txt valid, even if uppercase also works | Only uppercase endpoint works or lowercase endpoint returns wrong content | Confirmed file absent: NA, refer to 10.1. Failed requests: Human Check |
| 10.7 Is there a link in the robots.txt file to the sitemap index/sitemap? | At least one syntactically valid absolute HTTP(S) Sitemap URL | File present but no valid declaration | File absent: NA with reference to 10.1. Missing declaration is not proof sitemap does not exist |

For 10.2 the original wording asks whether pages are blocked, but Yes means the audit passes (no unintended blocking); Findings must make this explicit. Sitemap membership is the default intent evidence; do not require all page types to be present or classify each page before evaluating rules. A complete inventory can be evaluated against independently reliable rules without live-fetching every URL. Missing sitemap can use the documented fallback inventory; if neither inventory nor effective permissions can be verified, use Human Check rather than NA. An HTTP error alone does not turn a known-allowed rule result into robots No. Empty robots.txt is a user-specific audit defect, not an assertion that Google forbids empty files. A file with valid User-agent rules but no Disallow is not an empty file. Lack of sitemap declaration is an audit finding, not a claim the optional field is mandatory for Google. 10.7 checks the declaration, not every sitemap/child-URL response; independently observed sitemap-health errors are separate findings and coverage limits. Unknown raw text cannot prove a missing declaration.

10.3 uses the agreed finite rule-sample audit standard: selected enumeration examples all effectively blocked can establish Yes even before page existence is verified, provided no confirmed unused template directives or other 10.3 defects remain. Record each URL, source (observed/enumerated), matching group/rule and blocked/allowed/unknown result. Agent first chooses applicable sample families from the site nature and available evidence, then builds a finite baseline from those families and justified observed low-value variants. Cart, thank-you, admin, account and internal-search are an optional candidate menu, not universal requirements; do not include every main-crawl URL, the homepage, valuable categories or meaningful pagination as targets that must be blocked. Exclude verified nonexistent samples with the evidence/reason; record any omitted or untested material samples. Do not claim an empty sample set is an all-blocked pass. Zero non-empty effective Googlebot Disallow in a readable file establishes No under this standard even if the site has no verified special pages; recommend further validation rather than claiming exposure. An empty Disallow value is not a restriction. Do not pass solely because some named bots have Disallow: /. Partly unblocked synthetic samples require actual target/policy validation before calling them website defects; verified nonexistent samples can be excluded with evidence. Authentication and actual feature existence remain assessed under 10.5 and are not equivalent to Disallow. Not-found candidates are excluded, but 401/403/login redirects are access-control evidence or ambiguity, not absence. A 200 must be screened for soft 404 and generic homepage fallback. Report findings only when content/response corroborates classification.

## Default/plugin-generated rules are hints, not live functionality

A non-empty robots file may contain broad plugin/template rules unrelated to the site's current public features. Patterns such as /wp-content/uploads/wc-logs/, /woocommerce_transient_files/, /woocommerce_uploads/ and add-to-cart parameters suggest plugin-related intent, but do not prove an installed/active plugin, cart, account, exposed log directory or actual file existence. Do not label the entire file invalid solely from this pattern; confirm inapplicability before reporting the unused-template defect. Record the suspected template origin as an inference, not a verified platform/default attribution.

Separate three statements: a directive exists; it effectively matches a test URL for Googlebot; a real page/feature has been verified. A synthetic blocked /cart or ?add-to-cart URL proves only a rule match, not an active shopping cart. add-to-cart parameter rules also do not prove /cart or /checkout is blocked. A 200 response requires content corroboration and soft-404/homepage-fallback exclusion. Missing from sitemap alone does not prove absence. If obeying robots prevents content verification, do not turn blocking alone into existence evidence; record that limit or use a separately permitted diagnostic.

For 10.3 apply the finite rule-sample/no-Disallow standard above; a sample pass does not establish actual feature existence. For 10.5 apply cart policy only to verified cart objects/flow. If completed bounded discovery finds no verifiable cart and no live-flow clues, use cart subcheck NA with the attempted paths, sources and limitations; unresolved known flows or untested candidates are Human Check; do not give Yes just because generic ecommerce rules exist, or No because an assumed cart route is unblocked. Overall 10.5 still aggregates other applicable classes (e.g. admin), so cart NA does not automatically make the entire check NA.

Treat Allow: /wp-admin/admin-ajax.php as an exception whose actual effects are evaluated against required resource/function evidence. Its presence alone does not prove private admin exposure. Confirmed unused/inapplicable template directives are a 10.3 audit-standard configuration defect even without demonstrated crawl harm: set No/X, explicitly point out the residual directives and why they are inapplicable in Findings, and add a defect row in 10. Robot.txt. Keep discovery sources/counts in Coverage. Suspected remnants without sufficient applicability evidence remain Human Check in Checklist only. Report the actual directives and site-function evidence, not an invented security exposure or guaranteed ranking impact.

Example (conditional on actual evidence, not a claim about the user's example domain): Findings: 'Cart applicability unconfirmed; template rules alone do not establish ecommerce. Verify the shopping function.' Coverage: 'add-to-cart and plugin upload-path rules observed; scoped cart/checkout probes and crawl/sitemap links found no verified shopping flow. Other special-page classes assessed separately.'

## Site-aware sample selection for 10.3

Before matching rules or preparing a user-run candidate batch, the agent judges the site's nature using actual homepage/navigation/page content, crawl/sitemap routes, visible functions and explicit owner information. Site-type labels are a starting point, not proof that a feature exists. Record the inferred site nature, supporting evidence, selected families and excluded families/reasons in Coverage or the inventory; Findings contains only the resulting conclusion and its key reason. A user's explicit feature confirmation takes precedence over an inference.

| Site evidence | Appropriate sample selection |
| --- | --- |
| Public shopping/order flow | Cart/checkout and transaction thank-you candidates; account, internal search and filter variants only where relevant |
| Corporate/service brochure site without shopping clues | Do not require cart/checkout/order-success coverage. Use relevant observed internal search, lead-form thank-you, admin or low-value variants where supported |
| Content/news/blog site | Consider internal search, observed tags/archive/filter variants or admin routes according to their crawl-control purpose; preserve useful articles, categories and pagination |
| Membership/application portal | Consider actual login/account/private-function routes and low-value query variants; do not infer private exposure or require ecommerce paths |
| Mixed or uncertain site | Select supported families; keep materially uncertain features as identified gaps, without guessing nonexistent functionality or asking the owner to classify every ordinary page |

The collector's seed list is a candidate superset, not a mandatory checklist. Filter it for applicability before selecting samples, uploading List Mode URLs or treating an unblocked path as a finding. WordPress/WooCommerce template rules alone do not make shopping samples applicable. Synthetic samples within a selected applicable family can still support the agreed all-blocked rule-sample Yes without validating each page's existence. Verified nonexistent samples can be excluded. A materially unresolved selected family remains Human Check with completed work and gap details.

For a site without supported on-site ecommerce functionality, absence of cart/checkout restrictions is expected and is not a failure. Existing shopping-related rules do not count as applicable passing samples. If site/owner evidence confirms those rules serve no applicable current feature or retained crawl-control purpose, report “Unused/inapplicable robots template rules” as a confirmed 10.3 No and write the defect in 10. Robot.txt. Evidence includes exact groups/directives and the basis for their inapplicability; How to Fix removes only confirmed unused rules while retaining justified controls. Do not require demonstrated harmful effects before reporting this agreed configuration defect. A non-ecommerce label, missing sitemap route or WooCommerce-looking pattern alone is not enough to confirm every plugin/upload rule is unused: unresolved purpose is Human Check in Checklist only.

Decision precedence: confirmed unused/inapplicable template rules or any other confirmed 10.3 defect => No, even when all selected applicable samples are blocked. Suspected remnants are Human Check when no defect is confirmed. The existing no-Disallow audit rule is unchanged: zero non-empty effective Googlebot Disallow in readable robots is No with further validation, even when shopping is inapplicable. Its repair advice must reflect the actual site nature and must not recommend adding cart/checkout rules to a site without those functions. If effective restrictions exist but completed assessment establishes no applicable target/sample family, use a specifically justified inapplicability reason rather than a vacuous all-blocked Yes; unknown applicability is Human Check.

## Bounded candidate discovery

Use these seed suffixes beneath the root and observed locale prefixes, within configured budgets. They are examples to extend from actual site evidence, not a claim of exhaustive site discovery. Preserve real URLs/queries. Store tested/not-tested candidates, reasons and result counts in raw evidence.

| Class | Candidate suffixes |
| --- | --- |
| Cart | /cart, /basket, /shopping-cart, /checkout/cart, /checkout |
| Thank-you | /thank-you, /thankyou, /order/success, /checkout/success, /order-confirmation |
| Admin | /admin, /administrator, /backend, /dashboard, /wp-admin |
| Account | /account, /my-account, /profile, /login, /signin, /register |
| Crawl-control candidates | /search and observed filter/sort/search parameter variants |
| Pagination | /page/2, /?page=2, /?paged=2; actual /category/<observed-slug>/page/2 and next links from the inventory |
| Category | /category, /categories; actual category slugs and their observed sort/filter/pagination variants |

Duplicate content requires observed variants plus actual content comparison; a query parameter or matching title is not sufficient. No login, registration, form submission, order creation or private-account access. This is an SEO audit, not a penetration test or exhaustive sensitive-path scanner.

## Pagination/category variants and crawl loops

For 10.2 use sitemap URLs as the default intended-public inventory; do not require extra page-purpose confirmation for ordinary sitemap entries. Preserve valuable category landing pages and meaningful pagination needed to discover products/articles. /page/ or /category/ alone is not an automatic Disallow/noindex requirement. Distinct paginated item sets are not duplicates simply because the template/title is shared; do not recommend canonicalising all distinct pages to page 1. Verify relevant self-canonicals and page-specific responses where indexable pagination is intended.

Beyond the selected 10.3 baseline rule samples, and for actual-feature 10.5 assessment, inspect observed low-value filter/sort combinations, equivalent query/path representations, repeated/empty/out-of-range pagination, and recursive URL growth. Confirm actual content and crawl-control intent before reporting absent controls. Out-of-range page numbers should not repeat the last page or silently return a normal homepage; record the response/content evidence. Noindex and canonical do not themselves impose a hard crawl boundary.

For temporary discovery the agent must keep a visited/requested set, strip fragments from request identity, preserve path/query evidence and avoid unsafe lowercasing or indiscriminate query removal. Do not request a known URL twice, follow redirect/pagination cycles indefinitely, invent thousands of page numbers, or enumerate the Cartesian product of filters. Follow actual links; cap each pagination series at robots.pagination_pages_per_series and each category's variant sample at robots.variants_per_category, plus global page/depth/request limits. Exceeding an audit sample limit is a coverage limitation, not proof the site is defective.

Stop further expansion of a series when it cycles, points to already-tested pages, returns verified 404/410, or repeatedly serves the same confirmed item set/content for different page numbers. Use source/target link pairs, final destinations and actual item/content fingerprints; shared header/footer alone is insufficient. Keep counts and excluded families in Coverage, and fetch targeted evidence for a suspected site defect before writing an Issue.

These per-family limits are enforced by the agent's discovery workflow/SF scope configuration, not by the collector (which only generates a finite candidate list). For broad SF discovery configure actual scope exclusions/limits from observed patterns, or use staged bounded List Mode batches; do not claim this helper automatically controls an independent SF crawl.

## Bot-specific full-site blocking

Always inspect User-agent grouping, not just the presence/count of Disallow: /. A full-site rule applies to its matching bot group; many named groups without Googlebot or a matching wildcard do not establish Googlebot is blocked. Merge duplicate group names for counting; preserve raw line evidence and evaluate effective matching rules, including Allow exceptions. A high Disallow count is not an automatic defect threshold; zero non-empty effective Googlebot Disallow is the explicit 10.3 audit-standard exception.

Summarize bots blocked site-wide and distinguish search/index discovery, AI search/retrieval, training/extended-use controls, SEO/backlink tools and unknown/legacy names. Use current primary vendor documentation for roles; do not assign purpose solely from a bot's name. Google-Extended does not control Google Search inclusion/ranking. Applebot differs from Applebot-Extended. GPTBot differs from OAI-SearchBot, and user-triggered ChatGPT-User requests have different robots behavior; a listed rule alone does not prove actual service denial.

For 10.2, No is supported when an important live page is blocked for a bot the site's stated discovery policy requires. For 10.3, use its agreed baseline and additional verified restrictions, checking effective Googlebot groups rather than unrelated named-bot restrictions. Site-wide blocking of a required discovery bot is a separate cause from missing restrictions on low-value paths. Confirm required channels from user policy; do not silently make every named bot mandatory. Googlebot is the default required bot. Disclose other blocks, but unknown optional-bot policy alone does not make the Googlebot checks unresolved. For an explicitly requested/required additional channel whose intent or access remains unknown, write the precise question in Human Check and the handover. Restricted training or backlink tools alone need not be defects; omitted bots are not proof of real access through HTTP/WAF.

Confirmed policy conflict creates a defect row in 10. Robot.txt such as 'Required discovery bot blocked site-wide', naming the specific bot, applicable rules, affected public URLs and the intended channel. Describe potential restricted access, not proven ranking loss or absence from an index. Recommend adjusting only the conflicting group after owner policy is known, preserving intentional restrictions. Never recommend deleting every bot block solely because the list is long.

## CSS/JS identity, source scope and permission (10.4)

10.4 concerns CSS/JS necessary for the site's intended public/indexable pages. Do not turn every URL in Response Codes > Blocked by robots.txt into a CSS/JS finding. Keep three independent facts: URL/resource identity, its source-page relationship and scope, and effective Googlebot permission. A successful human/ignore-robots HTTP fetch does not establish crawler permission.

1. Establish resource identity using the SF resource type/content type and actual stylesheet/script source relationships. A .css/.js suffix alone is only a clue. An HTML login/reset URL is a page, not a stylesheet or script merely because it appears in a blocked export. Conversely, a stylesheet/script request that redirects to login HTML is not a valid asset response; if a public page needs it, report the unusable resource with its redirect/content evidence.
2. Link each resource to its actual source pages. Homepage, products, articles and other intended-public pages are the main scope. Verified resources exclusively used on intentionally excluded login/reset/admin/private pages can be excluded from 10.4 with reason and URLs; assess the page under 10.5. Never exclude a shared resource if any intended-public page needs it. A login/reset name alone does not prove admin/private purpose or exclusivity. No resource relationship data means a concrete Human Check gap, not an allowed result.
3. Determine effective Googlebot matching for the resource's own origin, group and most-specific applicable Allow/Disallow rules. A Disallow line alone is not enough if an effective Allow exception wins. Once effective blocking is confirmed, retain blocked status even if the helper/browser/ignore-mode crawl returns 200. Conflicting dated/current evidence needs a specific verification gap; do not silently label it allowed.
4. Aggregate only eligible resources: confirmed blocked required public-page resource => No and a defect row in 10. Robot.txt; all verified eligible resources allowed and usable => Yes with counts and excluded scope; verified no eligible resources => NA with reason; missing classification/relationships/permission results or SF errors => Human Check in Checklist. A No remains No even if other relationships need follow-up.

Blocked HTML login/reset pages themselves do not fail 10.4. Such a block can be intentional for 10.5, but does not prove authorization or page breakage. Robots controls crawler access, not human access or HTTP health. SF robots-blocked/no-fetch status is not an observed server 404/5xx. Judge page breakage only from actual response/redirect/content evidence. No login or reset submission is performed.

A resource defect row lists the blocked resource plus affected intended-public source URLs, applicable bot/group/rule and actual response evidence when available. Recommend changing only the conflicting resource restriction while preserving deliberate private-page controls; never recommend unblocking all admin/login routes to fix a public asset.

Primary rendering reference: https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics

## Special-page policies (10.5)

| Class | Accepted policy | Confirmed defect |
| --- | --- | --- |
| Cart | Effective Disallow (crawl control), or crawlable applicable noindex (index control) | Public verified cart has neither control |
| Thank-you | Ordinary page: effective Disallow or readable noindex. Private order data additionally requires access control | Neither SEO control for ordinary page, or confirmed unauthorized exposure of private order data |
| Admin | Protected functions/content require authentication/authorization. Public login page alone is not exposure | Confirmed protected admin function/content exposed without authorization; Disallow alone cannot protect it |
| Account | Private account content requires authorization. Public login/register pages should have effective Disallow or readable noindex under this audit policy | Confirmed private exposure, or verified public login/register page with neither SEO control |
| Duplicate content | Valid corresponding canonical, appropriate redirect or readable noindex; verified unnecessary crawl variants may be disallowed | Confirmed duplication without appropriate treatment, or wrong/unusable canonical destination |

Label whether accepted control limits crawling or indexing; do not claim Disallow guarantees no indexing. Disallow plus hidden noindex is not verified readable noindex. Apply bot-specific directives to Googlebot, not arbitrary bots. Do not infer that an account is protected solely from its URL name or that a 200 login page exposes private content.

## Findings, coverage and aggregation

Every NA explains the inapplicability and completed scope, e.g. 'Owner confirms there is no transaction flow; available crawl and tested candidates contain no contrary evidence. Transaction thank-you subcategory NA within this scope.' A known transaction-only flow that cannot be verified without an order remains Human Check, not NA; no transaction is performed. Never write 'page does not exist' solely from enumeration. Coverage includes counts, URL sources, full/sample scope, excluded variants, rendering mode and unverified flows. Private page classes that were not actually verified remain clearly qualified.

The item-specific 10.2/10.3 rules above take precedence over generic category aggregation. Any confirmed failing applicable class establishes No; all applicable classes passing with none unresolved establishes Yes; all classes inapplicable or with no objects after completed scoped discovery under delivery-boundaries.md establishes NA with reasons. Critical unresolved evidence prevents Yes; use Human Check when no defect is confirmed. Unknown/errors go to evidence_gaps.json and the final workbook with required evidence and next action; always export without waiting for resolution. Every Human Check uses concise Findings for conclusion, specific gap/reason and next action, while Coverage records already-checked evidence, counts, sources and unchecked/failed scope without repeating them in Findings; no review row is added to 10. Robot.txt. A confirmed No may coexist with missing evidence: retain No and its defect, with Human Check details only in Checklist Findings. Every No still creates a kind=defect row in 10. Robot.txt; NA creates none. Same defect may link to multiple checks. Do not invent security/crawl-budget impacts without relevant evidence.
